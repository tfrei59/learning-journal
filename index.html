Git: Staging, Committing, and Pushing

After making changes to files in a Git repository, the workflow to get those changes onto GitHub is three steps:

1. Stage changes

git add .

Stages changes — tells Git "I want to include these changes in the next commit." The . means "everything in this directory that's changed or new." Git has a two-step process: you first stage (add) changes to a staging area, then you commit them. Until you git add a file, Git sees it as changed but doesn't know you want to save it yet. You can also add specific files: git add Thomas_Frei_CV_public.tex stages just that one.

2. Commit changes

git commit -m "Update CV"

Takes everything you've staged and permanently records it as a snapshot in your local Git history. The -m "Update CV" is the commit message — a short description of what changed. Without -m, Git would open your text editor to type a message. Each commit gets a unique ID (a hash like 0073348) so you can go back to any version later. This only affects your local copy — GitHub doesn't know about it yet.

3. Push to remote

git push

Sends your local commits up to the remote repository on GitHub. Until you push, the changes exist only on your machine. Pushing is what makes them visible at github.com. If you committed but forgot to push, GitHub would still show the old version.

Summary

The full flow: add (stage what changed) → commit (save a snapshot locally) → push (upload to GitHub). Think of it like writing a document (add), saving it to your hard drive (commit), then emailing it to someone (push).

Full sequence for updating a file

# If the edited file is somewhere else, copy it in first:
cp /path/to/updated/file.tex ~/cv/

# Then:
cd ~/cv
git add .
git commit -m "Update CV"
git push

Useful variations

  • git status — see what's changed but not yet staged (check before committing)
  • git log --oneline -5 — see the last 5 commits
  • git diff — see what changed but hasn't been staged yet
  • git diff --staged — see what's staged but not yet committed
  • git push origin master — explicitly push the master branch (plain git push usually works once set up)

Hermes + HEY Email: Inbox triage and ongoing management

Set up Hermes (Wendell) to manage my HEY email account using the hey CLI. This entry documents what was configured, the triage workflow, and the automation put in place for ongoing management.

What was set up

  • HEY MCP server — registered hey mcp as a stdio MCP server in ~/.hermes/config.yaml under mcp_servers.hey. Provides 7 tools (mail, contacts, todos, calendars, journals, etc.) that Hermes can call directly. Requires restarting Hermes to discover the tools.
  • HEY CLI auth — confirmed via hey auth status. OAuth token stored in keyring, auto-refreshes. Valid through Oct 31, 2026.
  • hey-email skill — saved the triage workflow as a Hermes skill so Wendell repeats the same categorization logic every time. Contains sender classification reference (which senders go to Feed, Paper Trail, Set Aside, Reply Later, or stay in Imbox).
  • Cron: inbox monitor — a no-agent cron job (hey-inbox-check.sh) runs every 4 hours, checks the imbox count, and sends a Telegram alert when it crosses 50 threads. Prompts me to say "triage my inbox" to Wendell.
  • Cron: camera donation reminder — a no-agent cron job (camera-donation-reminder.sh) runs daily at 5pm, checks if the "Ship cameras" event is still on my HEY calendar, and if so sends a reminder email to tom@ridgend.org with shipping details. Stops automatically once the event is deleted (after I confirm shipment).

The triage workflow (HEY-native inbox zero)

  1. Fetch all imbox threads: hey box view imbox --all --json — parse data.postings[] for id, sender, subject, date, topic_id.
  2. Categorize by sender + subject:
    • The Feed (hey move <ids> --to feed): newsletters, content marketing, Substack, Patreon creator updates, recurring content senders (Daily Stoic, TLDR, Peter Attia, Huberman Lab, Ted Gioia, Marbin, Rick Beato, etc.)
    • Paper Trail (hey move <ids> --to papertrail): receipts, bills, bank statements, payments, shipping, security alerts, verification codes, tax docs, subscription confirmations
    • Set Aside (hey move <ids> --to setaside): event invitations, community/faith, self-sent reference, meeting minutes, things to keep but not act on now
    • Reply Later (hey move <ids> --to replylater): personal emails from real people needing a response, professional/counseling emails
    • Imbox (keep): ambiguous or needs direct attention — left for one-by-one walkthrough
  3. Batch move in groups of ~50 IDs per hey move call. Moving to any box but Imbox marks threads seen automatically.
  4. Walk through remaining items one by one using hey thread read <topic_id> --markdown. Wendell presents sender, subject, date, summary, and suggested action. I decide: reply, set aside, paper trail, mark seen, or keep.

Key commands

# Fetch all imbox threads
hey box view imbox --all --json

# Read a thread (uses topic_id, NOT posting id)
hey thread read <topic-id> --markdown

# Move threads to a box
hey move <id1> <id2> ... --to feed|papertrail|setaside|replylater

# Mark threads as seen
hey seen <id1> <id2> ...

# Search email
hey search "query" --in imbox --date last_7_days --markdown

# Check calendar
hey event day [date]

# Compose a new email
hey compose --to email@example.com --subject "Subject" -m "Message body"

# Reply to a thread
hey reply <thread-id> -m "Reply message"

# Create a calendar event
hey event add "Title" --all-day --starts-on 2026-10-20 --notes "Details" --repeat every_day

How to update this journal

This journal is a single HTML file (index.html) in a Git repository on GitHub. To add or edit entries:

1. Edit the file

Open ~/learning-journal/index.html in any text editor. To add a new entry, copy the template block (marked with <!-- ENTRY TEMPLATE in the HTML comments), paste it where you want it, and fill in the content. Update the table of contents at the top of the page if needed.

2. Save and push

cd ~/learning-journal
git add .
git commit -m "Add entry: [topic name]"
git push

That's it. The live page at tfrei59.github.io/learning-journal updates automatically within a minute or so after pushing.

3. View locally

To preview changes before pushing, open the file in a browser:

xdg-open ~/learning-journal/index.html

Who can edit this?

The repo is public, which means anyone can see it. But only I (the owner) can push changes directly. Other people can fork it or submit pull requests (proposed changes I'd review), but they cannot modify this version directly. Public = visible, not editable by others.
